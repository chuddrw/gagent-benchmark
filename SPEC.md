# MiniShop benchmark specification

Build a deterministic, in-memory MiniShop order service with four areas: cart, discounts, inventory, and checkout/orders. Represent all money as integer cents; quantities and stock counts are nonnegative integers, with requested purchase quantities strictly positive. Dates, time zones, payment providers, persistence, and network services are out of scope. Expose an end-to-end CLI demo calling the public APIs to purchase products.

1. **Cart:** Accept a catalog of `{sku, priceCents}` products and cart entries `{sku, quantity}`. Reject duplicate catalog SKUs, unknown SKU, invalid quantity and invalid price. A cart can contain multiple SKUs, and repeated add-to-cart requests for a SKU accumulate quantity. Compute deterministic line totals and subtotal without floating-point currency arithmetic. Empty cart cannot checkout.
2. **Discounts:** Implement percent-off coupon codes with a `{code, percent, minSubtotalCents, maxDiscountCents?}` definition. Codes are case-insensitive, at most one coupon per checkout, min spend checked against pre-discount subtotal, and percentage calculation uses `Math.floor(subtotalCents * percent / 100)` capped by `maxDiscountCents` if present. Reject unknown/ineligible codes. Final order total cannot be negative.
3. **Inventory:** Track available stock by SKU in memory. Reserve an entire list of requested items atomically: if *any* SKU cannot be reserved, no stock changes. No overselling, including simultaneous calls in a single Node process; reserve exactly once per successful order. Provide an idempotent reservation keyed by order ID, so a repeated checkout with the same ID cannot decrement stock twice.
4. **Orders:** Accept checkout input `{orderId, items, couponCode?}`, validate cart, price and coupon eligibility, then atomically reserve stock before returning a confirmed order `{orderId, items, subtotalCents, discountCents, totalCents, status:'confirmed'}`. If validation or stock reservation fails, do not create a successful order or alter inventory. A repeat with the same orderId and identical request returns the original confirmed order without reserving twice; a repeat with different data raises an error. Expose `getOrder(orderId)`. The cart, coupon, inventory, and order modules must interoperate through the shared public interfaces.
5. **Quality:** Build succeeds with `npm run typecheck`; tests pass with `npm test`; no hidden network calls. Errors must be structured (e.g. `{code, message}`), not silent success. Demonstrate success, coupon use, out-of-stock failure, and idempotent retry in `src/demo.ts` runnable with `npm run demo`.

## Public contracts
Predefine `src/types.ts` with the following **types**, and supply signatures in the four module stubs; teams are free to choose internal implementation details. Keeping a minimal stable external contract makes tests possible while leaving genuine integration work. If the product is intended to coordinate evolving interfaces, you may run a separate variant that leaves internal module interface decisions open, but use the same variant across A/B/C.

```ts
export type CatalogItem = { sku: string; priceCents: number };
export type CartItem = { sku: string; quantity: number };
export type CartTotals = { items: Array<CartItem & { priceCents: number; lineTotalCents: number }>; subtotalCents: number };
export type Coupon = { code: string; percent: number; minSubtotalCents: number; maxDiscountCents?: number };
export type DiscountResult = { discountCents: number; totalCents: number };
export type CheckoutRequest = { orderId: string; items: CartItem[]; couponCode?: string };
export type Order = { orderId: string; items: CartItem[]; subtotalCents: number; discountCents: number; totalCents: number; status: 'confirmed' };
export type ShopErrorCode = 'INVALID_INPUT' | 'UNKNOWN_SKU' | 'UNKNOWN_COUPON' | 'INELIGIBLE_COUPON' | 'OUT_OF_STOCK' | 'ORDER_ID_CONFLICT' | 'EMPTY_CART';
```

Suggested public functions/classes (actual starter `src/*.ts` stubs must establish exact signatures):
- `new CartService(catalog: CatalogItem[])`, `.add(sku, qty)`, `.totals(): CartTotals`.
- `applyCoupon(subtotalCents: number, couponCode: string | undefined, coupons: Coupon[]): DiscountResult`.
- `new InventoryService(initial: Record<string, number>)`, `.reserve(orderId: string, items: CartItem[]): void`, `.getAvailable(sku: string): number`.
- `new OrderService(cartCatalog: CatalogItem[], coupons: Coupon[], inventory: InventoryService)`, `.checkout(req: CheckoutRequest): Order`, `.getOrder(orderId: string): Order | undefined`.

Use `ShopError extends Error` with `code: ShopErrorCode` for shared errors. For idempotence, compare normalized checkout inputs (same SKUs/quantities even if item ordering differs), not the raw object identity. Whether a coupon omitted or undefined is equivalent should be explicit in acceptance tests.

## Frozen rulings

Acceptance tests enforce the decisions below. They close gaps in the brief so hidden tests do not invent unpublished rules. The same rulings apply to every condition.

1. **Valid numbers.** `priceCents` and stock counts are integers greater than or equal to zero, so zero is valid. A purchase `quantity` is an integer greater than or equal to one. Negative numbers, fractions, `NaN`, and infinities are `INVALID_INPUT`. An empty SKU or empty `orderId` is `INVALID_INPUT`. `minSubtotalCents` is an integer greater than or equal to zero. `maxDiscountCents`, when present, is an integer greater than or equal to zero.
2. **Identity.** SKUs are case-sensitive. Coupon codes are case-insensitive. The tests do not surround codes with whitespace, and trimming is not required. If several coupons match a code, the first one in the list is used. Coupons that are not selected are not validated.
3. **Construction.** Duplicate catalog SKUs make `CartService` and `OrderService` construction throw `INVALID_INPUT`. Invalid initial stock makes `InventoryService` construction throw `INVALID_INPUT`.
4. **Cart totals.** `totals()` with no accepted lines returns `{ items: [], subtotalCents: 0 }`. Totals are pre-discount. Each SKU appears once. `lineTotalCents` is `priceCents * quantity`, and `subtotalCents` is the sum of the line totals. A rejected `add` leaves earlier lines unchanged. Tests identify lines by SKU, not by array position. Callers' catalog arrays are left unchanged.
5. **No coupon.** Omitting `couponCode` and passing `undefined` are the same request. `applyCoupon(subtotalCents, undefined, coupons)` returns `{ discountCents: 0, totalCents: subtotalCents }` when `subtotalCents` is a valid integer greater than or equal to zero, including zero.
6. **Coupon math.** A selected coupon is eligible when `subtotalCents >= minSubtotalCents`. `percent` on that coupon is an integer from 0 through 100 inclusive; otherwise the call throws `INVALID_INPUT`. `discountCents` is `Math.floor(subtotalCents * percent / 100)`, then limited by `maxDiscountCents` when that field is present. `totalCents` is `subtotalCents - discountCents` and is never negative. An unknown code throws `UNKNOWN_COUPON`. A known code below its minimum throws `INELIGIBLE_COUPON` rather than returning a zero discount. The caller's coupon array is left unchanged.
7. **Stock.** `getAvailable` throws `UNKNOWN_SKU` when the SKU was not in the initial map. A SKU present with stock zero returns zero and can produce `OUT_OF_STOCK`. `reserve` of an empty list throws `EMPTY_CART`. Quantities for the same SKU in one request are added together. If any requested quantity cannot be reserved, `reserve` throws `OUT_OF_STOCK` or `UNKNOWN_SKU` as appropriate and changes no stock. A failed reserve does not record the order id. The same order id with the same summed items is a no-op regardless of item order or split lines. The same order id with different summed items throws `ORDER_ID_CONFLICT` and changes no stock.
8. **Concurrency.** In one Node.js process, stock checks and updates for a single `reserve` call become visible together before another call in that process observes them. Tests schedule reserves on separate event-loop turns. Stock must not become negative. This is not a multi-process transaction guarantee.
9. **Checkout.** There is no stored status other than `confirmed`. A failed checkout throws, stores nothing, and leaves inventory unchanged, so `getOrder` returns `undefined`. `items: []` throws `EMPTY_CART`. Success decrements the same `InventoryService` instance passed to the constructor and returns one aggregated `CartItem` per SKU. Invalid input and unknown SKUs are rejected before stock changes.
10. **Replay.** For an order id that is already confirmed, decide replay versus `ORDER_ID_CONFLICT` before reserving stock. The same normalized request returns the stored order and does not reserve again, even if current stock could not satisfy it. Normalization ignores item order, adds split lines for the same SKU, treats an omitted coupon and `undefined` as equal, and compares coupon codes without case sensitivity. A different request throws `ORDER_ID_CONFLICT`, keeps the original order, and does not change stock, even when that different request would also be out of stock. An order id whose earlier attempt failed may be used again. `getOrder` returns `undefined` for an unknown id. Mutating the caller's request object after checkout does not change the stored order.
11. **Errors.** Throw `Error` values with a non-empty `message` and a `code` from `ShopErrorCode`, using `ShopError`. `NotImplementedError` is only the unimplemented-stub sentinel. Its message is `Not implemented`. It is not a product error code.
12. **Demo.** `npm run demo` must show a successful purchase, a coupon purchase, an out-of-stock failure, and an idempotent retry by calling the public APIs, without network access. Acceptance tests do not lock the demo's stdout wording.
